# OntoKiln · Rust 本体编译与在线推理设计 v0.1

评审稿 · 2026-11-06

**首版交付两条可互相核对的查询链。** 给定组件属性和业务上下文，向上追到 Go 源字段，返回每一步的加工、实现选择和代码证据。反过来，给定一个源字段和相同上下文，查出哪些组件属性使用了它。两次查询固定在同一份编译快照上，使用同一套选择规则。

沿用前序讨论的部署条件，单个在线 Pod 配置为 8 vCPU / 32 GiB，Abase 单值上限按 4 MB 设计。系统读取 Turtle，按 Git 提交和泳道发布，Pod 在本地完成预热后切换。规模验收按 **1 亿条去重后的显式 RDF 三元组**，另计解析展开条数、推导事实数和属性派生数。本稿编写时仓库尚无业务 TTL 或基准结果，文中的业务样例为合成数据，容量和耗时为待验证目标。[前序技术讨论](chatgpt-conversation://6aedbaac-15d0-83e8-8f2b-34b3bed671e5)

## 1. 系统边界与数据流

```text
Go 分析器 / Ontology Foundry
  │  带版本的 TTL、TBox、业务规则、SHACL、源码证据
  ▼
Rust 编译任务 ── 校验报告、词表覆盖率、规模统计
  │  解析 → 外部排序与去重 → 语义映射 → 规则计算 → 建索引
  ▼
不可变 RuntimeBundle → Abase 分块 + 发布清单 → 泳道目标版本
                                                 │
                              Pod 下载、校验、组装、预热
                                                 ▼
                                  Rust 在线服务 / 快照句柄
                                  ├─ 字段血缘、影响、实现选择、解释
                                  └─ 已验收的只读 SPARQL 查询
```

| 责任方 | 输入与产物 | 关键约定 |
|---|---|---|
| Go 分析器 | Go 源码、构建标签、模块版本 → 有类型的符号、赋值、调用候选、分支条件、源码位置 | 复用 Go 的类型检查与 SSA。遇到反射、动态配置、未解析接口调用，输出带原因的边界记录 |
| 建模流水线 | 分析事实 → 现有本体词汇、映射配置、规则与约束 | Python 可继续编排。每份快照声明仓库提交、构建配置、分析器及词表版本 |
| Rust 编译器 | 固定快照 → RDF 索引、领域 IR、证据索引、发布清单 | 输出可重建，错误定位到输入文件、实体和规则。领域映射独立版本化 |
| Rust Runtime | 快照、属性 IRI、类型化上下文、工作量上限 → 结果与证明 | 在线只读。Abase 参与装载和版本发现，单次遍历只访问 Pod 本地数据 |

Go 的 SSA 提供指令和值的表示。字段是否跨组件传递、接口选中了哪个实现，仍需上游分析与业务映射给出依据。[Go SSA 文档](https://pkg.go.dev/golang.org/x/tools/go/ssa)

## 2. 从一个字段定义答案

以下为**合成样例**，仅用于约定行为。假设视图字段 `View.addressText` 在默认实现中取城市和地址详情拼接，定制实现取地址别名，另有一个在选中实现之后追加前缀的 Hook。

| 派生 | 输出 | 有序输入与加工 | 选择条件 | 证据 |
|---|---|---|---|---|
| D1 | `Base.text` | `Order.city, Order.detail → FormatAddress` | 默认实现 | E1，默认赋值 |
| D2 | `Base.text` | `Order.alias → MaskAlias` | `custom == true`，覆盖默认 | E2，定制赋值 |
| D3 | `View.addressText` | `Base.text → Copy` | `prefix == false` | E3，直接赋值 |
| D4 | `View.addressText` | `Campaign.prefix, Base.text → Prepend` | `prefix == true`，后置增强 | E4，Hook 赋值 |

* `custom=false, prefix=false` 时，血缘经 D3、D1 到达 `city` 和 `detail`。二者是一次加工的共同输入，证明须保留两个参数位置。
* `custom=true, prefix=true` 时，血缘经 D4、D2 到达 `prefix` 字段和 `alias`。此时从 `city` 反查，不能通过已被覆盖的 D1 报出这个视图。
* 仅给 `prefix=true` 时，`Campaign.prefix` 在此模型下确定参与。默认字段和别名分别带 `custom=false / true` 的剩余条件。查询结果可以同时包含确定来源与候选来源。
* 如果分析器只提供 `BuildAddress CALL AddressService`，返回调用上下文和缺失的字段映射。只有具备字段赋值或映射证据，才能把具体响应字段列为来源。

这里的“确定”始终指给定快照、已建模条件下的依赖。线上某次请求实际执行了哪条路径，需要与该请求匹配的运行时事实。

## 3. 编译输入与领域 IR

**输入契约。** 一次构建接收 `input-manifest`，列出逻辑文档 ID、文件摘要、基础 IRI、文件角色、代码仓库与 commit、泳道、构建标签，以及映射、规则和 shapes 的版本。文件角色区分数据、词表、规则和校验形状。映射配置按完整谓词 IRI 匹配，指定方向、输入序号、端点类型和证据字段。每类谓词统计“输入数 → 映射数 → 拒绝数”。未知的一般谓词仍可通过 RDF 查询。必需的业务映射缺失时阻止发布。

| IR 记录 | 关键字段 | 编译与查询约束 |
|---|---|---|
| Property | 公共 IRI、模型、符号路径、属性角色 | 把源字段、视图字段、中间值和静态分析边界分开。没有入边的属性只有显式标为源字段才算“已追到源头” |
| Derivation | 输出、操作、输入段起止、有序输入、可选 guard、实现绑定、证据集 | 每条记录表示一种产生输出的方式。多个参数是联合输入，同一输出的多条派生保留各自的分支语义 |
| Variant | 扩展点、候选实现、模式、优先级、guard、阶段与顺序、可用性、选择证据 | 区分默认、覆盖、增强与降级。绑定到具体派生，能解释某候选被屏蔽的原因 |
| Guard | 上下文字段、类型、运算与常量组成的表达式 | 首版支持布尔、枚举、相等、集合成员和逻辑组合。类型表随快照发布。动态条件可显式标记未知 |
| Fact / Rule | 关系、参数、规则版本、直接前提 ID | 显式事实与规则推导分别标记。物化时保留至少一个可回放的证明。可取证明的数量单独限额 |
| Evidence | 仓库、commit、路径、符号、行区间、提取器、来源记录 | 热索引仅保存 ID，解释时读取定位信息。多份证据可支撑同一事实。文件改名后仍按原 commit 解析 |

IR 分别编码 `CALL`、`DATA_FLOW`、`TRANSFORM`、`EXTEND`、`OVERRIDE`、`FALLBACK` 及其 guard。用 (输出 → 派生 → 输入) 建模，能在一个证明内同时保留数据依赖、选择依据和源码位置。业务接口暴露 IRI 或版本限定的证明引用，整数 ID 的有效域为单个 Bundle。

### 实现选择与条件传播

1. 每个扩展点先求值 guard 和可用性，取真、假、未知三值。上下文缺键产生未知，传入错误类型直接返回参数错误。保留未知的原因和剩余表达式。
2. 对互斥实现按显式优先级选择。候选的有效条件是自身可用且所有更高优先级候选均未生效。高优先级未知时，低优先级只能带条件返回。默认实现继承“没有覆盖生效”的条件。降级实现额外要求被指定的前序实现不可用。一次调用失败触发的降级，需要调用结果作为上下文输入。
3. 同优先级互斥候选同时成立时返回 `ambiguous` 和双方证据。静态能证实的冲突直接作为编译错误。增强按声明的前置/后置阶段和顺序连接到已选基线。缺少组合顺序且输出相互覆盖时，按冲突处理。
4. 沿路径传播条件的合取，同一结论的不同证明保留析取。例如一段要求 `custom=true`，后段要求 `custom=false`，该路径不可达。布尔或枚举条件归一为按字段约束的分支集合，剪除冲突，合并等价分支。遇上动态条件保留“待确认”。若表达式展开超过预算，标记结果不完整，禁止将其上升为确定。只有已证覆盖所有可行上下文才标记 `certain`，其余可行候选标记 `possible`。

## 4. Rust 编译流水线

| 阶段 | 实现与产物 | 验证或失败边界 |
|---|---|---|
| ① 解析与溢写 | `oxrdfio` 按文档流式读取 Turtle，各文件可并行，长文件顺序解析。定长批次写入临时有序段 | 保留 base/prefix 作用域。空白节点按逻辑文档隔离，匿名节点按文档内确定性分配。解析失败报告文件和位置 |
| ② 编码与去重 | 分段生成词条和临时 ID，外部归并唯一词条后按规范字节序赋全局 ID。通过磁盘映射表或排序连接重写三元组，再归并去重 | RDF 项编码包含种类、词法形式、datatype 和规范语言标签。数值相等的不同词法形式仍可区分。重复事实合并时归并来源 |
| ③ 映射与校验 | 从有序谓词段生成 Property、Derivation、Variant、Guard、Evidence。检查端点、参数次序、引用、规则安全性和扩展阶段 | 字段级断言缺证据时记录分析边界。违反必需映射或硬约束时整包不可发布。输出机器可读校验报告 |
| ④ 预计算 | 小规模 TBox 的 `rdfs:subClassOf`、`rdfs:subPropertyOf` 先按强连通分量折叠再求祖先。白名单规则可离线物化 | 记录每条规则的输入数、增量、轮数与证明空间。超过限额使该构建失败。ABox 上的任意多跳属性血缘在线按需遍历 |
| ⑤ 建索引与封包 | 用外部排序生成 RDF 索引和派生正反索引，同步生成度分布、谓词频率、字段覆盖率、段大小和热页清单 | 验证排序、CSR 哨兵、ID 边界、证据引用。执行黄金查询后生成内容摘要 |

**语义支持表。** 每个 Bundle 记录 `semantic_profile`，调用方可按版本核对能力。

| 资产 | v0.1 支持的执行语义 | 超出范围时 |
|---|---|---|
| RDF / RDFS / OWL 词汇 | 保存显式数据。编译上表的继承闭包，对声明的 `rdf:type` 和子属性事实按白名单传播 | 一般 OWL 公理可检索。要求执行 `sameAs` 等未支持公理的规则包须报错，避免误称完整 OWL 蕴含 |
| SHACL | 若 shape 读取推导事实，在预计算完成后校验指定数据图。首批支持 `targetClass` 配合单谓词路径及 `minCount/maxCount/datatype/nodeKind`。报告 focus、path、shape、severity | 显式声明校验图使用哪些物化事实。遇到未支持的必需 shape 则失败，可用同图的上游完整校验报告作为经配置的替代输入，绑定图与 shapes 摘要。[SHACL 规范](https://www.w3.org/TR/shacl/) |
| 业务 Rule IR | 有类型关系的正向 Horn 子集，头部变量必须在体部绑定，按连接键和统计量排执行顺序。正递归用半朴素迭代，新增集合为空即停止 | 优先级、缺省、回退交给实现选择器。任意代码、未声明算子或越界递归直接报错 |
| SPARQL | 首版以现有 `.rq` 清单验收只读查询，默认图为去重显式业务 RDF。规则物化结果仅在显式选择的派生图中可见。在线上下文结果由领域 API 返回 | 发布清单列出已验收查询及数据集语义。暂缓 Update、外部 SERVICE 和任意用户查询上线。[SPARQL 1.1 Query](https://www.w3.org/TR/sparql11-query/) |

例如白名单可声明规则 `type(x, parent) ← type(x, child) ∧ subClassOf(child, parent)`。每轮仅用至少含一条新增前提的连接生成候选，再减去已有事实。对首次产生的结论记录规则 ID 和直接前提，已有结论只按证明配额增补依据。

首版采用全量重建、不可变快照。数据删除、规则撤回和词表变更通过重建生效。可重用已校验的相同内容块。跨版本复用整数 ID 或仅重算局部传递闭包，需另行验证。构建重试复用带阶段摘要的完成段，输入哈希或工具版本发生变更时，该阶段及下游产物失效。用不同并行度重建同一输入，验证业务段逐字节相同。

## 5. RuntimeBundle 与亿级容量

| 本地段 | 布局与访问方式 |
|---|---|
| RDF 词典与索引 | 词条字节区、`u64` 偏移和支持 IRI→ID 的排序查找表。显式数据保留 SPO、POS、OSP 三种排列，按绑定前缀二分后顺序扫描。派生图另存有界增量 |
| 属性索引 | 用独立稠密 `PropertyId`。上游 CSR 从输出属性定位派生 ID，派生表给出输入槽位。下游 CSR 从输入属性定位 (派生 ID，槽位)，再取输出。两边引用同一 guard、实现与证据 |
| 选择及证明 | 扩展点 → 有序候选，guard 指令和常量池。证据目录与源码定位字符串分段。仅命中且要求解释时读取详情 |
| 辅助段 | 谓词基数、度数分位、类型候选集合。对反复求交且有收益的类型构建 Roaring 位图 |

统一小端、固定宽度、对齐，文件头含魔数、格式主次版本、段类型、记录数、偏移和长度。ID 默认 `u32`，预留哨兵，写入前检查上限，超过 v1 能力即拒绝构建。偏移和长度用 `u64`，加载器对加法、乘法和跨段引用做溢出与范围校验。文件以内容摘要命名，完成写入后才允许只读映射。替换版本时新建文件。内存映射会触发缺页，必须把实际驻留页计入容器预算。[memmap2 文件映射说明](https://docs.rs/memmap2/latest/memmap2/struct.Mmap.html)

**容量算例。** 设去重三元组数为 N、属性数为 P、派生数为 D、输入槽数为 I。在 N = 100,000,000 时，一份 `3 × u32` 排列为 1.20 GB，三份共 3.60 GB（3.35 GiB），其中 SPO 已是全量事实。若上游条目只存派生 ID、派生的输入段只存属性 ID、下游条目存派生 ID 和槽号，两套 CSR 偏移及这些条目约占 `16(P+1) + 4D + 12I` 字节，另计派生表头、词典、映射、证据和规则段。词典应按实际唯一词条字节和偏移测量，尤其要区别重复 URI 与长且几乎唯一的源码文本。

下表是**单 Pod 双版本切换的初始预算**，单位 GiB，按 cgroup 计费。热页数以预热轨迹测量，不能从文件大小或 mmap 虚拟地址空间推断。

| 项目 | 上限假设 |
|---|---:|
| 当前版本热页 / 候选版本热页 | 9 + 9 |
| 两版共用的查询工作区与结果缓冲池 | 3 |
| 服务堆、线程栈、路由及指标 | 2 |
| 装载、解压及额外文件缓存 | 2 |
| 其他计费页和运行波动 | 2 |
| 合计 / 距 32 GiB 的余量 | 27 / 5 |

运行时以实测 `memory.current`、峰值、file/anon 分项以及 major faults 校验预算。在同一 cgroup 内避免将 RSS 与文件缓存重复相加。热页超额时优先把候选版本预热到新 Pod，readiness 通过后按泳道迁移流量。编译使用独立任务，按可用内存设排序批次、并发数和归并路数。临时磁盘预检分别计入原始段、归并输入和输出、生成的索引及保留的旧版本。估算依据为样本中每条语句和每个词条的实际字节数。

## 6. 在线执行与接口

请求进入时一次性取得泳道快照的强引用，解析公共 IRI 和上下文，之后所有算子、证据查找和序列化均使用此引用。用有界 CPU 工作池执行查询，网络线程承担 I/O。每个请求有 deadline、访问边数、状态数、证明字节和结果数配额，全局工作区不足则排队或返回限流。客户端断开或超时会取消 CPU 任务并归还配额。

| 操作 | 执行计划 | 可解释结果 |
|---|---|---|
| `POST /v1/lineage` | 从输出查上游 CSR，逐条派生应用实现选择与 guard，展开有序输入，直到源字段、证据缺口、环或预算边界 | 来源集、加工与选择证明、未解析边界 |
| `POST /v1/impact` | 从输入查下游 CSR，在每个派生输出所属的扩展点重新判定胜出实现，再沿输出继续 | 模型下确定或可能受影响的属性、所属组件和成立条件。表示输出依赖该输入，值是否改变取决于加工函数 |
| `POST /v1/reachable` | 给定两个属性和方向做有界搜索，允许命中后早停 | `certain / possible / unreachable / unknown`。模型内完整搜索且所有可行分支均排除时才给出 `unreachable` |
| `POST /v1/resolve` | 按扩展点取候选，看 guard、优先级、阶段与可用性 | 生效实现、候选、被屏蔽原因、冲突及缺失上下文键 |
| `explain=witness` | 随上述领域查询返回一份有界证明。联合输入逐槽记录，汇合部分按节点引用复用 | Rule、Derivation、选择记录和 Evidence 可定位到固定 commit。遇环用回引标记 |
| `POST /v1/sparql` | v0.1 按查询模板 ID 和 RDF 类型化参数执行。`spargebra` 解析，`spareval` 访问 Bundle 数据集 | 保留 SELECT 解映射的重复数、未绑定变量及显式排序等语义。与领域结果按各自的数据图和上下文解释 |

**遍历和证明分开计费。** 工作队列按 (属性、选择环境、归一化剩余条件) 去重，同一属性经不同可行分支到达时分别处理。用广度优先队列先处理较浅状态，以保留可用的跳数。相同状态再次到达只增加证明引用。设实际访问状态数为 K、这些状态的邻接展开数为 L，已有稠密 ID 的遍历基本工作量为 O(K+L)，另计选择求值、条件合并和证明输出。查询先求来源集合，按需为每个来源取有限见证。列举全部路径可能呈指数增长。环本身不能证明某属性是源字段。

**接口样例。** 下例继续使用第 2 节合成字段。前端传 IRI、泳道和上下文，响应给出模型依据。示意中的短版号和证据定位表示同一测试快照。

```json
{
  "lane": "test",
```

`complete` 表示请求范围内的候选集合是否完整，单个来源的 `status` 表示该依赖能否在所给上下文中确定。缺上下文可以完整返回一组条件候选。深度、工作量或输出上限提前截断，或静态分析遇到未解析源头时，返回 `complete=false` 及 `boundaries[{reason, at}]`。若仅证明被裁剪，单列 `proofComplete=false`。若一个来源仅在多条互斥分支合起来时才确定，解释须给出覆盖全部可行分支的证明，或明确指出返回的见证仅覆盖其中一支。SPARQL 达预算时终止并返回结构化错误，避免把部分结果作为完整 SELECT/ASK 答案。

已绑定快照的响应均携带 Bundle ID（SPARQL 可用响应头）。允许请求方指定 `expectedBundleId`，已切换则返回 409，便于多次查询一致地比较。其他错误包括未知属性 404、上下文类型错误或不支持的算子 422、资源队列已满 429、无就绪版本 503。源码证据与查询复用泳道及代码仓库的访问控制，返回源码定位前校验调用方权限。

**SPARQL 适配可独立验收。** `QueryableDataset` 需要实现 triple/quad 模式查找及 RDF 项双向转换。Bundle 词典 ID 可直接参与匹配。查询临时生成或词典外的字面量由请求级表示承载。明确区分默认图、指定命名图和任意命名图，全未绑定模式只能在预算内扫描。执行器内部的排序或聚合也可能分配内存，单靠限制索引迭代次数不足以限额。首版仅开放已测模板，较重的模板放入可取消、可限制内存的独立 worker 进程，共享同一组只读文件。用独立 Oxigraph 实例离线比对，部署包按验证过的 crate 组合锁定。[Oxigraph 各组件](https://github.com/oxigraph/oxigraph) · [QueryableDataset 接口](https://docs.rs/spareval/latest/spareval/trait.QueryableDataset.html)

## 7. 发布、热切换与回滚

1. **写不可变内容。** 先把段切块，再对每块独立做 zstd 压缩，检查最终写入 Abase 的 key/value 协议开销和实长。按 4 MB 取保守字节上限并可配置。不可压缩数据超限时继续拆块。每块记录压缩摘要、原长、段内偏移，每段另记完整 SHA-256。4 MB 只约束传输，查询按本地 CSR 与排序索引访问。
2. **发布完整清单。** 上传缺少的内容块并验证可读，再写不可变 manifest。manifest 包含源 commit 与泳道、规则/映射摘要、编译器版本、格式版本、段与块顺序、计数、容量估算及预热查询。清单过大时分成同样受限的清单页，根清单保存页摘要。Bundle ID 取规范编码的根清单内容摘要，自身 ID 与构建时间等非确定性元数据置于封装外。
3. **推进泳道目标。** 以 `(lane, generation, bundleId)` 记录期望版本。已校验清单才可推进 generation，回滚也创建更高 generation 并指向旧包。控制面需具备条件写或带 fencing token 的单写者。Abase 的条件写能力待平台确认，否则将目标指针置于已有的强一致发布服务。不可用时保持现有目标。
4. **Pod 准备候选。** 下载到临时目录，限制并发与解压总长度，校验块和段、格式、引用边界。完成文件和目录的 fsync 后原子重命名至本地版本目录，再 fsync 父目录。mmap 后预触达查询所需热页，并运行有已知答案的探针，检查延迟与内存余量。坏块只重试该块，持续失败标记此次准备失败。
5. **切换与回收。** 每泳道串行处理发布事件，切换前重新核对最新 generation，丢弃过期准备结果。新请求从 `ArcSwap<Bundle>` 获取新版，已在执行的请求持有旧版至结束。Pod 报告 active generation 和预热结果。切换原子性以单 Pod 为单位，跨 Pod 严格读一致时由路由按 Bundle ID 选已就绪实例。旧请求排空后释放映射，磁盘保留最近已验证版本供回滚。[arc-swap 文档](https://docs.rs/arc-swap/latest/arc_swap/)
6. **恢复与清理。** 下载中断或磁盘不足时继续用已激活版本。重启优先验证本地持久化的最近就绪指针，临时目录可丢弃重建。全新 Pod 待首包预热成功才就绪。跨版本内容块按仍受保护的 manifest、进行中的上传租约及回滚保留期做标记清理。上传失败和重复通知均可重试。

核心监控分三组。编译记录各阶段耗时、临时磁盘峰值、未映射谓词、缺证据率和规则膨胀倍数。查询按操作记录 P50/P95/P99、访问边数、条件状态数、截断与未解析比例、证明大小。发布按泳道记录目标与就绪 Pod 数、装载阶段、双版本峰值和回滚耗时。区分“上游不知道”和“执行超预算”，这两类问题分别需要修复模型与执行计划。

## 8. Rust 工程拆分

| 模块 | 首版职责 | 依赖选择 |
|---|---|---|
| `model` | 类型化 IR、上下文 schema、规则和格式契约 | Rust newtype 隔离不同 ID 域。Serde 编解码元数据 |
| `compiler` | RDF 解析、磁盘归并、词汇映射、规则计算、索引生成 | `oxrdfio/oxrdf` 解析。Rayon 限并发处理独立排序段。小型规则依赖图可用 petgraph。[Turtle 规范](https://www.w3.org/TR/rdf11-turtle/) · [oxrdfio 流式解析接口](https://docs.rs/oxrdfio/latest/oxrdfio/struct.ReaderQuadParser.html) |
| `bundle` | manifest、段读写、校验及只读映射 | memmap2、SHA-256、zstd。将映射安全前提和格式边界校验集中在此模块 |
| `runtime` | Lineage、Impact、Resolver、证明和预算。SPARQL 适配 | 有序切片、CSR。按分析结果启用 roaring。SPARQL 复用 spargebra / spareval |
| `service` / `cli` | HTTP、调度和快照管理。离线编译、校验、探针 | Tokio、axum、arc-swap。暴露独立的存储适配接口，测试使用本地目录，集成环境接 Abase |

首版提供两个入口。工程师用 `ontokiln compile/verify/query` 重放构建、验证快照和诊断单次查询，`ontokilnd serve` 用于线上只读服务。优先复用 RDF 解析与 SPARQL 求值。Rust 自研范围集中在有序段构建、领域映射、选择器和可解释遍历。某个递归规则族出现重复连接瓶颈后，再用同一事实集比较 Datafrog 等实现。

## 9. 实施顺序与验收

| 阶段 | 可运行交付物 | 进入下一步的条件 |
|---|---|---|
| M0 · 固定样本 | 收集一个提交下 `BuyV2_DeliveryServiceBody` 的脱敏 TTL、关联映射、源码位置、`view_component_context.rq`、案例 `7034901202` / `7372472817` 的预期答案 | 逐条标注源字段、加工、条件、证据和排除路径。现有 SPARQL 只校对其能表达的事实，覆盖与降级由代码或领域负责人独立确认 |
| M1 · 纵向原型 | 本地 `compile → verify → lineage/impact`。跑通真实组件和第 2 节合成夹具 | 默认、覆盖、增强、回退、未知条件、参数顺序、证据缺口与环路均有反例。每条确定结论有见证，已屏蔽字段零误报 |
| M2 · 索引及兼容 | 外部排序、规则白名单、mmap、只读模板 API。100 万/1,000 万规模实验 | 同输入重编产物一致。与离线 Oxigraph 比较冻结 `.rq` 结果及 bag 语义。伪造长度、坏摘要、悬空 ID、未知必需 shape 均拒绝 |
| M3 · 亿级与发布 | 1 亿去重显式三元组，在 8C/32 GiB 运行查询混合和持续流量下的版本切换。接入 Abase | 通过下表初始目标。坏块、旧通知、进程重启、回滚、双版本内存不足均有演练，按请求统计跨版本混读为零 |

**测量方法。** 真实抽样统计词条基数与字节分布、属性派生率、热点度数、条件未知率和证据长度。放大数据时使用可复现种子并保留这些分布，另外构造超级节点、深链、环和互斥分支。每个规模分开测冷启动、预热稳态、切换中三种状态，记录输入摘要、平台、磁盘、编译总时间、峰值内存/落盘量、产物大小、预热时间与查询延迟。只有真实样本能验证字段语义，大规模合成数据用来验证资源上限。

下表是**首轮验收目标**。以并发 8、每轮稳态 30 分钟为起点，常规组预设每请求最多 5 跳、1 万条访问边、100 个结果。单独压测并发 1/32、超大扇出和超预算查询。混合流量初始取血缘 40%、影响 20%、实现选择 15%、实体检索 10%、白名单 Join 10%、带规则证明 5%。同时报告完成率、限流率、截断率和 P99，将排队与序列化计入端到端耗时。用于延迟验收的常规组须获得完整且正确的预期结果。

| 测项 | 起始门槛 | 判定依据 |
|---|---|---|
| 语义正确性 | 两个黄金案例及分支反例逐项通过 | 比较字段、联合输入、剩余条件、被排除候选和证据行。同一条件下正反向查询互相印证 |
| 实体检索 / 高选择性 2～3 关系 Join | 热态 P95 分别 < 5 ms / < 30 ms | 单独报告每个模板的基数、结果量和耗时 |
| 有界 3～5 跳血缘或反向影响 / 规则推导带证据 | 热态 P95 分别 < 100 ms / < 200 ms | 输出证明能定位源字段与选中实现，同时记录 P99、每请求工作集 |
| 容量与版本切换 | 单 Pod 稳态和同 Pod 切换峰值目标 ≤ 27 GiB，无 OOM，切换中答案版本一致 | 超出双热预算时单列新 Pod 预热方案的额外资源和延迟，同 Pod 指标记为未通过 |
| 装载和故障 | 未完成预热的版本接收 0 个请求，坏包激活次数为 0 | 在旧版本持续流量下破坏分片、延迟发布和并发回滚，再检查就绪状态及每次响应的 Bundle ID |

**第一个决策点在 M1。** 如果真实 TTL 只能证明服务调用，先补上游字段赋值、条件和代码证据，再扩大数据规模。如果字段及证据已齐备但血缘错误，先修正映射或选择器。进入 M3 前还需取得 Abase 实际单值计量、发布指针能力、Pod 临时磁盘和预期流量分布，用实测值替换本稿预算。
