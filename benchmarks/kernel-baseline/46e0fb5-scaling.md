# 编译与推理规模基线：百万、千万实测与亿级推演

2026-11-13。固定引擎提交 `46e0fb5b6089e9f5bacb8494437c956e21e936a2`，release/default features。本轮目标是建立可信的编译与规则物化基线、检验单位事实成本与资源增长，再推演亿级所需条件；没有据此实施内核性能优化。

## 1. 怎样判断规模增长是否可接受

编译必须读取输入、建立词典和索引，物化必须计算并写出新增事实；总耗时随输入和输出增长是必要成本。本轮观察的核心是 **吞吐、每条输入事实成本、推导放大率、候选工作量、迭代轮数以及资源峰值**。

用有效指数描述相邻规模的观测增长：

$$
\alpha=\frac{\log(T_{10M}/T_{1M})}{\log 10}.
$$

指数接近 1 表示在这两档数据上接近线性；这是观测量，不是算法复杂度证明。三次重复只支持中位数与实测范围，不能产生有意义的 p95/p99、置信区间或容量保证。

## 2. 同一配置、固定二进制

两档都使用 4 GiB combined RSS、8 GiB scratch、300 秒单操作预算，max_derived_facts=10,000,000、max_intermediate_rows=100,000,000、max_iterations=100；单线程、串行，每阶段三次独立进程。所有十二个正式样本均 COMPLETE 并通过对应计数/产物 oracle。

环境为 Linux x86_64、Rust 1.95.0，CPU 型号 AMD EPYC 9V74，可见 9 个 vCPU、约 9.73 GiB 物理内存；执行只使用配置的一条计算线程。工作目录与 scratch 在 overlay 文件系统，底层物理设备未识别。不清 OS page cache，本轮构建、测试和审计均在计时之外；外部宿主负载和物理存储状态未受控制，不将这组数称为冷盘测量或常驻服务吞吐。

引擎二进制 SHA-256 与干净 `46e0fb5` release 构建记录一致，驱动在开始前校验二进制和完整 kernel identity。扩展驱动只派发冻结 harness 的 Full compile/materialize 阶段，并记录自身与冻结方法的 hash。环境记录中的源工作树包含未提交的基准/报告文件；这不等于重新构建了引擎，实际被测二进制以 hash 和构建记录为准。

先前 512 MiB 基线与本报告分开保存。内存预算会改变内部缓存：SQLite main/temp cache 各为预算的 1/8，词典缓存估算阈值为 1/16。因此扩大到 4 GiB 后分别约为 512 / 512 / 256 MiB，必须同时重测百万档作为锚点。不能把原 512 MiB 的百万数据与这里的千万数据拼成增长曲线。

## 3. 输入与规则工作量

输入生成器每档恰有 10 条 schema、每订单/客户记录 10 条事实，所有事实唯一。两级类/属性继承、固定短字面量与三个显式正规则；每组最多 8 个 next 节点，尾部 self-loop。扩容增加短链数量，不增加链深。输入是合成 RDF 与固定规则，尚未纳入实际业务本体的全部 SPARQL `.rq` 资产及治理 SHACL 编译负载；这里的规模结论不代替那些资产的端到端验收。

| 显式事实 | 订单数 | 输入 GiB | 新增事实 | 最终事实 | 迭代 | 规则求值 | 累计 join 候选 |
|---|---|---|---|---|---|---|---|
| 1,000,000 | 99,999 | 0.112 | 862,490 | 1,862,490 | 8 | 136 | 1,862,482 |
| 10,000,000 | 999,999 | 1.122 | 8,624,990 | 18,624,990 | 8 | 136 | 18,624,982 |


当前负载推导放大率约为 0.8625，最终事实约为输入的 1.8625 倍。累计 join 候选计数不等于 SQLite 内部扫描行数；max_intermediate_rows 限制单次 delta 查询与每轮 next 规模，不是累计计数上限。数据生成、输入摘要和答案核对不在操作计时之内。

## 5. 阶段成本与资源

下表阶段时间为三次成功样本的中位数；RSS/scratch 为三个记录峰值中的最大值。engine 与 parse/index 重叠，不能再次相加；各阶段中位数之和也不一定等于整体中位数。RSS 是预算使用的 combined RSS，不是 PSS；scratch 是采样峰值，不是瞬时峰值证明。

| 事实数 | 阶段 | 内部时间 s | 最大记录 RSS GiB | 最大记录 scratch GiB |
|---|---|---|---|---|
| 1,000,000 | Full 编译 | parse 3.484; index 4.227; engine 7.712 | 0.290 | 0.234 |
| 1,000,000 | Full 物化 | reasoning 9.375 | 0.359 | 0.280 |
| 10,000,000 | Full 编译 | parse 39.583; index 44.976; engine 83.970 | 1.184 | 3.469 |
| 10,000,000 | Full 物化 | reasoning 109.083 | 1.052 | 4.207 |


Full 的全量词典、raw/facts/source_facts、frontier/next 在 SQLite；Rust HashMap 是有估算阈值的词典缓存，不把全部事实收进 Rust Vec。SQLite 使用 temp_store=FILE，具备超过缓存后继续落盘处理的基础。cache_size 是缓存目标，不限制所有分配；词典清空也保留 HashMap 容量，所以不能从配置相加推导严格 RSS 上界。

物化为落盘半朴素过程，但每个 SCC 会复制 facts 到 frontier，每条多 atom 规则有多个 delta 位置；预算 COUNT 与 INSERT 会分别执行 join，候选再去重，最终还维护索引、ANALYZE/VACUUM。固定八轮的当前负载能解释增长趋势；长链和高扇出规则不满足同一假设。

实现证据固定于被测版本：[编译/物化](https://github.com/Codefor/ontokiln/blob/46e0fb5b6089e9f5bacb8494437c956e21e936a2/src/full.rs)、[冻结/完整性](https://github.com/Codefor/ontokiln/blob/46e0fb5b6089e9f5bacb8494437c956e21e936a2/src/full_artifact.rs)、[预算监管](https://github.com/Codefor/ontokiln/blob/46e0fb5b6089e9f5bacb8494437c956e21e936a2/src/full_execution.rs)。

## 6. 亿级时间情景

使用当前完整批次的千万档中位数为锚点，分别列出单位成本保持、最近有效指数保持、N log N 形状参考：

$$
T_{100M}^{linear}=10T_{10M},\quad
T_{100M}^{empirical}=T_{10M}^2/T_{1M},\quad
T_{100M}^{N\log N}=10\frac{8}{7}T_{10M}.
$$

这三项不是上下界或置信区间，N log N 也不是已证明的完整引擎复杂度；它们是相同数据、规则、闭包形状下可复核的规划情景。

| 操作 | 单位成本保持，分钟 | 经验指数保持，分钟 | N log N 参考，分钟 |
|---|---|---|---|
| Full 编译 | 15.70 | 16.88 | 17.95 |
| Full 物化 | 21.49 | 25.09 | 24.56 |


### 存储和缓存条件

以下把千万档逻辑字节或最大记录 scratch 乘十，仅用于同形数据的容量规划起点；不是保证的资源上界。Full artifact 包含冻结 RDF、规则、plan 和清单。

| 项目 | 10M 实测 GiB | 100M 线性情景 GiB |
|---|---|---|
| 输入 | 1.122 | 11.217 |
| Full 编译 SQLite | 1.174 | 11.737 |
| Full 编译 完整产物 | 2.295 | 22.953 |
| Full 编译 scratch 采样峰值 | 3.469 | 34.690 |
| Full 物化 SQLite | 1.543 | 15.425 |
| Full 物化 完整产物 | 2.664 | 26.642 |
| Full 物化 scratch 采样峰值 | 4.207 | 42.067 |


亿级输入和单个数据库会超过本机约 9.73 GiB 的可见物理内存；输入、索引、工作副本不可能全部留在页缓存中。千万档已经出现不同块读取量，不能把缓存命中的百万耗时直接乘一百。没有设备吞吐、等待和更大工作集的实测，这些时间情景可能明显低估真实耗时。

RSS 不按十倍外推：固定预算的缓存会饱和，但 SQLite 排序、语句、词项和其他分配仍可能触及预算。磁盘则需同时容纳原输入、保留的 compiled/reasoned 与当前操作临时区。scratch 不是整个工作目录容量；索引构建、frontier/next、VACUUM、快照复制会在若干阶段并存。

8C32G FaaS Pod 需按其实际 CPU 配额、内存与本地存储重新测量；本次单线程结果不能按核数折算为八倍吞吐。分片存储传输、跨 Pod 预热、常驻实例挂载与并发请求也不在本次计时边界内。

同形 100M 的预期推导事实为 86,249,990，最终事实 186,249,990。亿级目标超过当前 max_derived_facts=10M 上限，冻结输入本身也将超过 8 GiB scratch；三种时间情景均明显超过 300 s。这些预算需要在亿级实测前重新设定。Full 使用 i64 词项 ID / SQLite 计数和 u64 统计，100M 不是整数表示上限问题。

### 推理形状的限制

固定短链扩容保持迭代轮数与局部 fanout。若改成随输入增长的长链，传递闭包输出本身可能平方增长；多对多关系会放大 join 候选；更大的 schema、规则 SCC、更多来源重复、命名图、长字面量和更高词项基数也会改变成本。完整 OWL 也不在本次 rdfs-supported-v1 加正规则的测量范围内。

因此本次能支持的结论是：已测规模和负载下的编译/物化吞吐、资源与增长曲线；对亿级给出带条件的情景，并把缓存、磁盘和闭包形状列为必须验证的门槛。一般本体库的亿级吞吐稳定性仍需真实工作负载和亿级完整实测确认。

## 8. 产物校验与记录完整性

正式计时结束后，以 release 内核使用的同一 SQLite 3.54.1 静态库读取六个保留产物身份：扩展批次的百万/千万 compiled 与 reasoned，以及原 512 MiB 基线的百万 compiled 与 reasoned。数据库以只读模式打开，`query_only=ON`，所有 SELECT 在读取事务内执行。实际总量、`explicit` 标记、默认图以及逐谓词分组均直接查询数据库，不以 manifest 计数代替观察结果。

| 输入 | compiled：显式 / 推导 / 总量 | reasoned：显式 / 推导 / 总量 |
|---|---|---|
| 1,000,000 | 1,000,000 / 0 / 1,000,000 | 1,000,000 / 862,490 / 1,862,490 |
| 10,000,000 | 10,000,000 / 0 / 10,000,000 | 10,000,000 / 8,624,990 / 18,624,990 |

16 个显式谓词分组、reasoned 的 7 个推导谓词分组均逐项匹配冻结生成器的独立公式；非法显式标记和非默认图事实均为零。每个身份另检查 20 个主体的完整出边多重集，覆盖 schema、链起点/边界、中点与末尾；compiled 的 80 条、reasoned 的 141 条预期关系全部匹配，比较包含词项词法、图与显式标记，不依赖内部词项 ID。

六个数据库及 manifest 的前后 SHA-256 均一致。原 512 MiB 与扩展批次的百万产物字节相同，因此实际对四种不同数据库内容执行 SQL，复用相同内容的观察，同时保留六个报告/路径/样本身份及各自的前后 hash。所有审计发生在计时之外。

[完整审计 JSON](46e0fb5-fact-audit.json)保存了 SQL、参数、期望、观察、身份及只读断言；[C 读取器](sqlite_audit.c)和[原始审计编排脚本](run_audit.py)按执行时字节归档。编排脚本保留本次环境路径作为取证记录，复现时需将输入报告、冻结 checkout、SQLite 库和保留产物路径映射到新环境。审计验证全量计数/谓词分布及确定性抽样关系，不声称逐条证明了全部推导事实，也不覆盖未抽样关系的完整语义等价。

首个扩展批次在第十二个请求写出 response 和测量 checkpoint 前意外消失，原因未知；最后可用 checkpoint 有十一个成功样本，工具会话已不可用，未发现残留基准或内核进程。没有把它改成 COMPLETE、补造计时或归因于引擎预算。随后使用相同二进制、方法和配置完整重跑；本文主统计只采用完整批次，不拼接两批样本。

[中断批次原始 checkpoint](46e0fb5-scaling-interrupted.json)与[独立中断观察记录](46e0fb5-scaling-interruption.json)一并保留。之前进度消息中的中断批次数字应以本文完整批次为准。

先前 512 MiB 全功能基线中的百万级 SPARQL COUNT/inferred 分组在约 60 s 终止，五项 SHACL 触及 RSS 预算。这里的编译/物化测量与直接 SQL 审计不能当作这些 API 路径的性能通过。并行提交的常驻快照、SPO 索引、SHACL 导航以及 CONSTRUCT 准入修复均未混入被测二进制；它们的 [10K/100K 对照报告](../kernel-20261113.md) 独立保留，不能把其中收益套入本次固定内核的规模曲线。

## 9. 复现与后续比较

从独立的 `46e0fb5` checkout 取得冻结 harness，并按构建记录准备同一 release 二进制。驱动校验 harness 固定 hash 及传入构建记录中的 binary/kernel identity：

```sh
python3 -B benchmarks/kernel_scaling.py \
  --harness /path/to/ontokiln-46e0fb5/benchmarks/kernel_baseline.py \
  --build-receipt benchmarks/kernel-baseline/46e0fb5-linux-build.json \
  --binary /path/to/ontokiln-46e0fb5/target/release/ontokiln \
  --output data/kernel-scaling.json --work-dir data/kernel-work \
  --sizes 1000000 10000000 --build-samples 3 \
  --memory-mib 4096 --scratch-mib 8192 --timeout-seconds 300 \
  --max-derived-facts 10000000 --max-intermediate-rows 100000000 \
  --max-iterations 100 --threads 1 \
  --build-profile release --build-features default --keep-work-dir
```

新引擎应使用自己的可核验构建记录与新编译产物，冻结方法、预算和输入不变后，每侧各自编译、物化再比较；升级二进制不会给旧不可变数据库自动增加新索引。A/B 工具检查同一报告 schema、阶段集合、冻结 harness/driver hash、输入、预算、计时与环境；失败、缺样本、未过 oracle 或不足三次样本不报告提升百分比。

```sh
python3 -B benchmarks/compare_kernel_baseline.py \
  benchmarks/kernel-baseline/46e0fb5-scaling.json data/kernel-scaling-after.json
```

不同预算、file/session transport 或测量方法需要分别报告。相同记录也不能保证相同物理宿主负载和存储设备状态。基线建立后，性能工作应先用这些原始数据定位瓶颈并验证单一假设；本轮以基线、独立正确性校验和规模推演为交付边界。
